## 2. 信息架构与导航设计

### 2.1 放哪里

PCL 当前顶部导航是 5 个扁平项（`FormMain.xaml:120-130`）：

```
[启动] [下载] [联机] [设置] [更多]
  Tag0   Tag1   Tag2   Tag3   Tag4
```

「社区游戏」有两个选择：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 顶层导航项（推荐）** | 在「联机」后插入「社区游戏」 | 曝光最高，符合“社区专属”定位 | 导航变成 6 项，窄窗口下略挤 |
| B. 放进「更多」子页 | 复用 PageOtherLeft 的列表 | 不改导航 | 入口深，社区属性弱 |

推荐 **A**，理由：社区服务器是核心卖点，且 PCL 的 `联机`（Tag2）目前被硬编码隐藏（`PageSetupUI.xaml.vb:447`），实际可见项只有 4 个，加一个变 5 个，正好回到设计容量。

### 2.2 页面布局（保持扁平）

PCL 的扁平风格 = 顶栏导航 + 右侧单页内容（无左侧二级列表时用 `PageChangeAnim(New MyPageLeft, FrmXxx)`，参考联机页 `FormMain.xaml.vb:1478-1480`）。

建议：

```
┌──────────────────────────────────────────────────────────────┐
│  [启动] [下载] [社区游戏] [设置] [更多]                        │
├──────────────────────────────────────────────────────────────┤
│  社区游戏                     [全部] [生存] [创造]  [刷新] 12:30 │
│                                                              │
│  ┌──────────────────────────────────────────────────────┐   │
│  │ 🟢 栎木主世界            1.20.1 · Forge               │   │
│  │    mc.limlin.cn:25565                                 │   │
│  │    ┌ MOTD 两行富文本（颜色/图标）─┐                    │   │
│  │    │ 欢迎来到栎木栎林～「有趣，有温度」 │                 │   │
│  │    └──────────────────────────────┘                    │   │
│  │    在线 12 / 100   延迟 38ms                           │   │
│  │    👤 shee33 · 🧑 A · 🧑 B · … 等 12 人（采样）        │   │
│  │    ⚠ 注意：需正版验证；请先安装社区整合包              │   │
│  │                                   [一键加入] [复制 IP]  │   │
│  └──────────────────────────────────────────────────────┘   │
│                                                              │
│  ┌──────────────────────────────────────────────────────┐   │
│  │ 🔴 栎木创造服（离线）    mc2.limlin.cn:25565           │   │
│  │    上次在线：今天 11:02    [重试]                       │   │
│  └──────────────────────────────────────────────────────┘   │
└──────────────────────────────────────────────────────────────┘
```

要点：

- **单页 + 卡片列表**，不引入左侧二级菜单，符合扁平风格
- 卡片状态：`查询中`（骨架）/`在线`/`离线`/`超时`/`未知`
- 顶部有「最后更新时间 + 手动刷新」；自动刷新只在进入页面时触发
- 分组用横向筛选 chip（全部/生存/创造/活动服），不做树形结构
- 「一键加入」本期可先置灰（Tooltip：即将开放），避免用户点了没反应

### 2.3 与「联机」页的关系

「联机」（EasyTier）和「社区游戏」（固定服务器列表）是两件事，建议分开，不要合并。若未来联机页重新启用，二者可以互相跳转。

## 3. 数据模型设计

### 3.1 服务器清单（服务端 → 客户端）

推荐**全量快照**（而不是增量），理由：删除天然可表达、客户端无需维护本地补丁状态、回滚简单。

```jsonc
{
  "schemaVersion": 1,
  "revision": 42,                  // 单调递增，客户端据此判断是否需要更新
  "updatedAt": "2026-11-25T03:30:00+08:00",
  "channel": "stable",             // stable / beta
  "minLauncherVersion": "0.1.9",   // 低于此版本的客户端忽略本快照（可选字段）
  "servers": [
    {
      "id": "limlin-main",         // 稳定唯一 ID，禁止复用
      "name": "栎木主世界",
      "group": "生存",             // 用于筛选
      "ip": "mc.limlin.cn",        // 域名或 IP
      "port": 25565,               // 可省略，默认 25565
      "notes": "需正版验证；请先安装社区整合包",   // 管理员手写，多行
      "order": 10,                 // 排序权重，小的在前
      "enabled": true,             // 紧急下架开关
      "authHint": "正版",          // 展示用：正版 / 离线 / 皮肤站
      "game": {                    // 一键加入所需（本期只存不用）
        "version": "1.20.1",
        "loader": "forge",
        "loaderVersion": "47.2.0",
        "modpack": {
          "url": "https://.../limlin-pack.mrpack",
          "sha1": "…",
          "size": 12345678
        }
      },
      "motdOverride": null,        // 可选：离线时展示的静态 MOTD
      "icon": null                 // 可选：自定义图标 URL（默认用 favicon）
    }
  ]
}
```

设计要点：

- `id` 稳定、不可复用；删除服务器 = 从快照移除（客户端下次同步即消失）
- `enabled:false` 用于**紧急下架**（比删除更温和，客户端可显示“维护中”或不显示）
- `notes` 与 MOTD 分离：MOTD 来自服务器实时数据，`notes` 来自管理员
- `game` 字段本期只存不用，等一键加入时直接可用，避免二次改协议
- `order` 显式排序，避免依赖数组顺序（JSON 编辑容易打乱）

### 3.2 客户端本地缓存

```
<PCL 数据目录>\PCL\Community\
├── servers.json        # 最近一次成功同步的快照
├── servers.meta.json   # { etag, lastCheck, revision, lastGoodAt }
└── servers.pending     # 下载中的临时文件（原子替换用）
```

- 写入流程：先写 `.pending` → 校验（JSON 合法 + schema + 签名）→ 原子替换 `servers.json`
- 任何一步失败：保留旧文件，界面标注「数据可能不是最新」
- **安装包内置一份默认快照**（嵌入资源），保证首次运行无网也能看到内容

## 4. 同步机制设计（重点）

### 4.1 推荐方案：GitOps 静态 JSON + CDN

```
管理员改 JSON → Git PR → CI 校验(schema/唯一id/字段范围) → CI 签名 → 发布到 CDN
                                                              ↓
客户端：按 TTL / 手动刷新 / 启动时低优先级拉取 → ETag 协商 → 校验 → 原子替换
```

**为什么不用自建 API 服务**（初期）：

| 维度 | 静态 JSON（推荐） | 自建 API |
|---|---|---|
| 成本 | 几乎为零（对象存储/GitHub raw） | 需要服务器、域名、运维 |
| 可用性 | CDN 自带高可用 | 自己保证 |
| 版本审计 | Git 历史天然可查 | 需自己做 |
| 实时性 | 秒级~分钟级（CDN TTL） | 秒级 |
| 动态能力（在线人数等） | 不能 | 可以 |

社区服务器数量有限、变更频率低，**静态 JSON 完全够用**。后续若要做“在线人数趋势/公告推送”，再引入 API。

### 4.2 触发时机

| 场景 | 行为 |
|---|---|
| 启动时 | 低优先级后台检查（延迟 5~10s，不阻塞启动） |
| 打开「社区游戏」页 | 若距上次检查 > TTL（建议 1 小时）则自动检查 |
| 手动点刷新 | 强制拉取（带 `Cache-Control: no-cache`） |
| 离线 | 使用本地缓存，页面标注「离线模式」 |

### 4.3 校验与防投毒（建议做）

- **HTTPS 强制** + 只允许白名单域名
- **JSON Schema 校验**（id 格式、port 范围、URL 必须 https）
- **签名**：客户端内置公钥（Ed25519 或 RSA-2048），服务端对 `servers.json` 的规范化字节签名；签名文件 `servers.json.sig`
  - 好处：即使 CDN/域名被盗用，也无法推送恶意服务器地址
  - 私钥只放 CI Secret，人工不接触
  - 若初期嫌麻烦，可以先用「HTTPS + schema 校验」过渡，但**强烈建议上线前就做签名**
- **sha1 校验**：`game.modpack` 的下载包必须带 sha1，安装时校验（复用 `FileChecker`）

### 4.4 多源与容灾

```jsonc
// 客户端内置的源列表（按顺序尝试）
[
  "https://cdn.limlin.cn/launcher/community/servers.json",   // 主 CDN
  "https://raw.githubusercontent.com/shee333/LimlinCL-Data/main/servers.json", // 备用
]
```

- 主源失败自动切备用，全部失败保留旧缓存
- CDN 建议设 `Cache-Control: max-age=60`，客户端加 `If-None-Match` 省流量
- **回滚**：`git revert` + CI 重新发布，客户端下次同步自动回到旧版本

### 4.5 版本兼容与灰度

- `schemaVersion`：客户端不认识的更高版本 → 拒绝更新并提示升级启动器
- `minLauncherVersion`：低于该版本的客户端忽略快照（避免老客户端解析新字段出错）
- `channel`：`stable` / `beta`，客户端设置里可切换（内部测试用）

### 4.6 客户端合并策略

同步只**替换整份服务器列表**，不做字段级合并。理由：

- 管理员在服务端就是“最终真相”，客户端本地不应缓存可编辑的服务器信息
- 但**本地额外状态**要保留：
  - 上次查询到的在线人数/延迟（用于离线时展示“上次在线”）
  - 用户是否收藏/置顶（本地私有数据，单独文件存）

## 5. MOTD 查询（服务器状态）设计

### 5.1 协议

用 Minecraft 标准的 **Server List Ping（SLP）**：

```
TCP 连接 → [VarInt 长度][Handshake(id=0x00, protocol=-1, addr, port, next=1)]
         → [VarInt 长度][Status Request(id=0x00)]
         ← [VarInt 长度][Status Response(id=0x00, JSON)]
```

响应 JSON 关键字段：

| 字段 | 用途 |
|---|---|
| `description` | MOTD（字符串或 chat component，需递归取 text/extra） |
| `players.online` / `players.max` | 在线/最大人数 |
| `players.sample[]` | 玩家名采样（**服务器可伪造/截断，UI 必须标注“采样”**） |
| `version.name` / `version.protocol` | 显示版本；protocol=-1 表示不匹配 |
| `favicon` | base64 PNG，卡片左侧图标 |
| `enforcesSecureChat` / `previewsChat` | 可选提示（正版/聊天签名） |

### 5.2 实现要点（.NET Framework 4.8）

- `TcpClient` + `NetworkStream`，**超时 5~8 秒**（PCL 的 HTTP 层 `NetRequestByClientRetry` 不适用于 TCP，需要新写一个小工具）
- 并发上限 **4~6**（`SemaphoreSlim`），避免同时扫几十个服把对方打挂
- 失败重试 1 次（间隔 1~2s，加随机抖动）
- 结果缓存 **30~60 秒**，页面内多次切换不重复查询
- **SRV 记录**：Minecraft 客户端会查 `_minecraft._tcp.<域名>`。.NET Framework 无原生 SRV API，需 `DnsQuery` P/Invoke 或引入小型库；建议 P1 再做，P0 只支持 `host:port` 显式端口
- **IPv6**：`TcpClient.ConnectAsync` 支持 `[::1]:25565`，注意解析 `[` 包裹的地址
- **基岩版（Bedrock）**：UDP RakNet 查询，协议完全不同。若社区有基岩服，需要在数据模型里加 `edition: "java" | "bedrock"`，P1 再实现

### 5.3 MOTD 渲染

- 旧式颜色码：`§0~§f`（16 色）、`§l §o §n §m §k`（样式）
- 新式：`§#RRGGBB` 十六进制（1.16+）
- PCL 是 WPF：用 `TextBlock` + `Run` 逐段着色（不能直接塞进 `Text`）
- chat component 的 `extra` 数组需递归；`translate` 类型（如 `multiplayer.player.joined`）可退化为显示 key
- 解析失败时退化成纯文本（去掉 § 码）

### 5.4 隐私与展示

- 玩家列表来自服务器主动返回的 `sample`，**不是权威数据**；UI 文案要写「采样」
- 若管理员不希望公开玩家名，可在数据模型加 `showPlayers: false`
- 在线人数以 SLP 返回为准，卡片上同时显示「查询时间」

## 7. 管理员运营流程

### 7.1 发布流程（建议）

```
1. 管理员编辑 servers.json（Git 仓库）
2. 提 PR → CI 自动检查：
   - JSON Schema
   - id 唯一且格式合法
   - IP/端口合法、URL 必须 https
   - 对每个 enabled 服务器做一次 SLP 预检（防止发布死链）
   - 检查 modpack sha1 长度与可达性
3. 合并 → CI 签名 → 上传 CDN（主 + 备）
4. 客户端 1 小时内（或手动刷新）拿到新数据
```

### 7.2 常见操作对照

| 操作 | 做法 | 客户端表现 |
|---|---|---|
| 新增服务器 | 快照里加条目，`revision+1` | 下次同步后出现 |
| 修改（换 IP/改 notes） | 改同 id 的字段 | 下次同步后更新（玩家无感） |
| 临时维护 | `enabled:false` | 显示「维护中」，不参与状态查询 |
| 永久下线 | 从快照删除 | 下次同步后消失 |
| 紧急撤回 | `git revert` + 重新发布 | 下次同步后恢复旧状态 |
| 强制立即生效 | 客户端「手动刷新」 | 立即拿到 |

### 7.3 建议配套

- **管理端小工具**（可后做）：本地编辑 JSON → 一键校验 + 签名 + 预览
- **发布记录**：Git commit 就是变更记录，排查问题时直接看 history
- **监控**：CI 定时跑 SLP 预检，服务器掉线可在群里告警（可选）

## 10. 需要你拍板的问题

1. **服务器规模**：预计多少个社区服务器？（十几个 → 简单卡片列表；上百 → 需要虚拟化列表 + 搜索）
2. **是否有基岩版服务器**？（决定是否从 P0 就引入 `edition` 字段与 UDP 查询）
3. **托管在哪**：自建 CDN / 对象存储 / GitHub raw？（国内可达性差异大）
4. **是否做签名**：建议做。私钥放 CI Secret，你能否接受维护这套？
5. **玩家列表是否展示**：SLP 的 sample 可被服务器伪造，展示可能引起误解
6. **「游玩注意」的展示位置**：卡片内常驻，还是点开详情看？（信息多时建议后者）
7. **一键加入的安装策略**：强制用社区整合包，还是允许“仅版本匹配就加入”？
8. **是否需要管理员后台**：本期用 Git 编辑 JSON 是否可接受？还是需要可视化后台？

## 11. 风险提示

1. **MOTD 查询的可用性**：服务器可能限流/封禁高频查询，务必并发受限 + 缓存 + 抖动；首次上线前用 CI 预检确认不会把服务器打挂
2. **玩家列表不可信**：SLP sample 由服务器掌控，存在伪造/截断；UI 必须标注“采样”
3. **同步链路单点**：静态 JSON 依赖 CDN，建议双源 + 内置快照
4. **协议更新风险**：SLP 协议长期稳定，但 `description` 格式与 hex 颜色随版本变化，解析要有降级策略
5. **合规**：服务器 IP 公开、玩家名展示、以及“社区服务器”内容本身需要你方确认无风险
6. **不要在前端执行任何来自服务端的字符串**：MOTD 只作为文本渲染，绝不解析成 XAML/命令

## 12. 托管方案调研（2026-11，面向国内用户、免备案）

> 需求：托管一个几 KB 的 `servers.json`，国内用户可稳定拉取，成本尽量低。
> 关键政策：**不备案就无法使用国内 CDN 节点**，这是硬性限制；免备案方案只能走境外节点或对象存储默认域名。

| 方案 | 备案 | 费用 | 国内速度 | 稳定性 | 结论 |
|---|---|---|---|---|---|
| **腾讯云 EdgeOne（国际站）Pages** | 免备案 | 免费 | 中（境外节点） | 较好 | ✅ 推荐做**主源**起步 |
| 腾讯云 EdgeOne（国内站）免费套餐 | 需备案域名 | 免费套餐 | 快 | 好 | ✅ 有备案域名后升级为主源 |

**推荐组合（双源 + 兜底）**：

1. **主源**：腾讯云 COS 默认域名（免备案、国内快、成本≈0）
2. **备源**：EdgeOne 国际站 Pages（免备案、免费）或 GitHub raw + 代理
3. **兜底**：安装包内置快照

客户端内置源列表按顺序尝试，任一成功即用；证书与数据都用 HTTPS + 签名校验，不依赖单一域名安全。

**GitOps 流程不变**：管理员改 Git 仓库中的 `servers.json` → CI 校验/签名 → 上传到 COS + EdgeOne 两个位置。
### 3.3 SRV 记录：隐藏真实端口（已实现）

若不想暴露真实 IP 与端口，可给域名配置 SRV 记录：

```
_minecraft._tcp.mod.limlin.art.  SRV  5 0 32407 nop.mc6.cn.
```

客户端写法（`servers.json` 中省略 `port`，或显式 `"useSrv": true`）：

```jsonc
{
  "id": "limlin-main",
  "name": "栎木主世界",
  "ip": "mod.limlin.art",   // 只写域名
  "group": "生存"
  // 不写 port → 自动查询 _minecraft._tcp.mod.limlin.art
}
```

行为：

- 查询 SRV 记录，用返回的目标与端口做 MOTD 查询
- **界面只显示域名**（不含端口），鼠标悬停可看到实际解析目标
- SRV 无记录/查询失败 → 回退到 `域名:25565`
- 显式写了 `port` → 不使用 SRV，按指定端口直连
